# 在线备份维护说明（审查修订稿）

> **发布状态：不核准。** 本文件描述一次在线备份对外成立所必须满足的协议；当前
> `backup.py` / `reclaim.py` 与这些条款的差距见第 8 节和 `REVIEW.md`。在差距关闭前，
> `complete.json` 只表示"备份进程未报错"，**不**表示副本可恢复到声明版本。

## 1. 目录与对象

目录库 `catalog.db` 保存 `head`（当前版本）、`snapshots`（版本存在性）和
`manifest`（版本、分区、对象名、摘要）。`data/` 中的对象不可变，文件名为载荷摘要；
相同载荷跨分区、跨版本共用同一对象，**再次引用不换名、不重写**。提交只追加版本，
不改写已有对象和已有版本目录。历史版本只在所需对象尚未回收时可读。

## 2. 一次成功备份必须同时满足的不变量

- **I1 版本一致**：副本 `catalog.db` 的 `head` 版本必须等于回执 `complete.json` 的
  `version`，也必须等于备份声明的版本。
- **I2 覆盖完整**：回执 `files` 必须恰好覆盖声明版本 `manifest` 的对象集合，不缺不多；
  每个对象的摘要必须与 `manifest` 一致。
- **I3 恢复一致**：`restore` 返回的 Lake 的 `version()` 必须等于声明版本，`read()`
  必须等于声明版本的完整行集合（由输入批次覆盖语义独立计算，不能用摘要或文件存在代替）。
- **I4 前进不干扰**：选定版本后，正常提交与回收必须继续推进，且不得使该次备份失败、
  串版或改变已完成副本；不得用暂停提交/回收来"实现"保护。
- **I5 事务边界**：载荷复制（读源对象、写目标对象）不得跨目录写事务；不得把前台
  `read` 的读/写长事务直接当作备份保护。
- **I6 失败语义**：受控复制失败不得留下可接受的完成标记；保护必须在成功和失败路径都
  释放；残缺目录的清理责任必须明确。

## 3. 版本选择与目录快照

**现状（不满足 I1）**：`backup.py:20-24` 在一个短事务里读 `head` 与 `manifest` 后释放，
`backup.py:25` 发出 `backup.selected`，`backup.py:26` 才复制 `catalog.db`。若在
`backup.selected` 回调中发生提交，复制到的是新目录，而回执仍声明旧版本。之后所有文件
摘要都能通过，`complete.json` 仍会写出（`backup.py:42`），但 `restore` 得到的目录
`head` 与回执版本不同：轻则缺文件 `FileNotFoundError`，重则行列碰巧一致而版本错误。

**必须**：声明版本、对象清单和目录快照来自**同一个快照**。兼容做法是把目录快照前移：
先复制 `catalog.db`，从复制出的目录读取 `head` 与该版本 `manifest`，以此作为声明版本和
对象清单，再登记对象保护并发出事件。也可以在同一 SQLite 连接上让选择事务覆盖目录快照，
但不得在 `backup.selected` / `backup.catalog` 回调期间持有会阻塞提交的写事务；提交前必须
释放。事后"发现目录版本变了就让备份失败"不可接受，因为并发提交是正常操作（I4）。

## 4. 对象保护的取得与释放

**现状（不满足 I2/I4）**：备份只保存对象名，不登记任何保护。`reclaim.plan` 只按当前
`head` 判断存活（`reclaim.py:4-6`），因此备份选完版本后的一次正常提交即可让旧对象成为
回收候选，`sweep` 删除它，备份在 `backup.py:35` 读取时失败。

**必须**：备份在开始复制载荷之前，以短事务登记其声明版本所需的全部对象（如目录库内
`pins(token, object)` 表或等价的旁路注册表），并在 `finally` 中按 token 全部释放——成功、
受控复制失败、摘要不符、目标写入失败都要释放。登记/释放只做元数据，不得跨载荷 I/O 持有
目录写事务。回收的 `plan` 与 `sweep` 都必须尊重活动保护。保护只需覆盖本进程这次备份；
任意进程崩溃后的残留保护清理不在本题范围，但必须在文档中写明由运维清理。

## 5. 回收裁决

`plan(lake)` 只是**建议清单**：它在自己的快照里读取 `head` 和存活集，返回当时未存活且
未被保护的 `data/*.jsonl`。候选产生后允许提交与备份交错，因此计划时的"死"在删除时可能
已经"复活"——同摘要载荷再次被新版本引用时，对象名不变，不会生成新文件。

**现状（不满足 I4，且直接损坏当前版本）**：`sweep` 逐个文件 `BEGIN IMMEDIATE` 后只检查
`path.exists()` 就 `unlink`（`reclaim.py:11-21`），不复核当前 `head`，也不看 `manifest`
或保护。旧候选被后续 `return` 再次引用后仍会被删。这不是只影响备份：直接调用
`plan → commit(return) → sweep` 会让当前版本 3 的 `read()` 抛 `FileNotFoundError`。

**裁决顺序必须**：`BEGIN IMMEDIATE` → 文件不存在则跳过 → 读取当前 `head` 版本的存活集，
仍存活则跳过 → 对象被活动备份保护则跳过 → 才 `unlink` → 提交。即删除决定在**删除时刻**
于写锁内基于当前引用和保护做出，而不是沿用 `plan` 时的结论。

## 6. 受控复制失败

`fail_at=N` 在复制第 N 个文件之前抛 `OSError`（`backup.py:33-34`），属于受控失败，不是
进程崩溃。当前行为：

- 不写 `complete.json`，`restore` 因缺少完成标记抛 `FileNotFoundError`，不完整目录被拒绝；
  这一点满足要求，原断言保留。
- 目标目录在第 9-10 行创建，失败后残留 `catalog.db`、`data/` 中已复制文件与
  `events.json`；没有活动保护可释放，也**没有定义**谁负责清理。
- `events.json` 在 `finally` 写出（第 49 行），是失败证据，不应在清理前丢弃。

**责任划分（建议并应写入运维流程）**：

| 事项 | 责任方 | 要求 |
| --- | --- | --- |
| 失败后是否可恢复 | `restore` | 无 `complete.json` 一律拒绝；不得以目录中文件齐全为由放行 |
| 保护释放 | `backup` | `finally` 按 token 释放，任何异常路径都不遗漏 |
| 残缺目标目录清理 | 调用方/运维 | 先保留并检查 `events.json`，再由调用方删除；备份任务不把残留目录登记为可用副本 |
| 恢复失败后的残缺目录 | 调用方/运维 | `restore` 在 mkdir 后失败会留下部分目录；由调用方清理，不得当作已完成备份 |

`complete.json` 建议用临时文件加原子替换写出，避免部分写入留下"看似存在"的完成标记；
这只是加固，不能替代 I1/I2 的校验。

## 7. 恢复与校验

`restore` 只接受有完成标记的目录（`backup.py:54`）。仅逐文件核对摘要（第 58-62 行）
**不足以**证明副本对应声明版本：它没有核对回执版本与复制出的 `catalog.db` 的 `head`，
也没有核对 `files` 是否覆盖声明版本的完整对象集合。恢复应显式执行：

1. 读回执，确认 `version` 为整数、`files` 非空且无重复对象；
2. 复制目录后确认副本 `head == receipt["version"]`，否则拒绝；
3. 确认回执对象集合恰好等于该版本 `manifest` 的对象集合，否则拒绝；
4. 逐对象核验摘要后写入，再用副本自身 `read()` 核对行集；
5. 任一步失败都抛出异常并保持"无完成标记可用"的语义，由调用方清理残缺目录。

## 8. 当前实现差距（发布阻断）

1. **F1 版本/目录快照分裂**：`backup.py:20-26`。`backup.selected` 后的提交进入副本目录，
   却不进入回执；完成标记仍写出。见 `REVIEW.md` 的 `case:commit-after-select`、
   `case:return-after-select-rows-deceive`。
2. **F2 无对象保护**：`backup.py:29-40` 与 `reclaim.py:4-6`。正常提交加回收可让备份在
   复制中途 `FileNotFoundError`。见 `case:commit-and-gc-after-select` 等。
3. **F3 回收候选不复核**：`reclaim.py:6`、`reclaim.py:17-18`。同摘要再次引用后旧候选仍被删，
   当前版本损坏。见 `case:stale-candidate-live-sweep-before-backup`、
   `case:stale-candidate-sweep-at-catalog`。
4. **F4 恢复校验不足**：`backup.py:54-63`，见第 7 节。
5. **F5 失败责任未定义**：`backup.py:9-10`、`backup.py:45-49`，见第 6 节。
6. **F6 文档原有承诺失实**：旧版本"目录一致+摘要正确即代表声明版本可恢复"和"备份无需
   参与回收协议"的表述已删除，改为本文件的不变量与裁决顺序。

## 9. 验证入口

- `python3 checks.py verify`：保留正常提交、历史读、静止备份、复制失败断言。
- `python3 checks.py repro`：保留原入口，稳定输出 `BACKUP_RESTORE_MISMATCH` 并退出 1，
  作为缺陷基线证据；本轮不修生产代码，不把它改成通过。
- `python3 evidence_gate.py record` / `verify` / `demo`：按 `review_cases.json` 重放
  原 `lab.exercise`，核对源码定位、报告引用与已保存的 `review.json`，展示真实恢复结果。
- 所有结论必须依据实际 `restore` 后的 `version()` 与 `read()`，不能只看摘要、文件存在或
  `complete.json`。合法交错、单因失败、组合掩盖分别见 `REVIEW.md` 用例矩阵。
